# Named Pipe IPC Mechanism

## Summary

The named pipe subsystem in `libgraph_server_shared.so` implements a
unidirectional data channel from the native graph server to the Electron
renderer process. Named pipes are used specifically for **analyzer terminal
output** -- the text stream that protocol analyzers (and high-level analyzers)
produce during analysis. This is NOT part of the main IPC mechanism (which uses
either in-process DriveRequest/PopResponse or WebSocket). Named pipes are a
secondary, data-only channel that bypasses the JSON message protocol.

## Source Path

```
/workspace/monorepo/graph-io/core/named_pipe/src/named_pipe_unix.cpp
```

## Class Hierarchy

Two classes implement the named pipe abstraction:

- **`Saleae::NamedPipe`** -- abstract base class (RTTI: `N6Saleae9NamedPipeE`)
- **`Saleae::NamedPipeUnix`** -- concrete Unix implementation using POSIX FIFOs
  (RTTI: `N6Saleae13NamedPipeUnixE`)

NamedPipeUnix inherits from both NamedPipe and `std::iostream`, making it
simultaneously a stream interface and a pipe abstraction.

## Pipe Naming Convention

Pipes are created as POSIX FIFOs in `/tmp/`:

```
/tmp/{namedPipeIdentifier}
```

The `namedPipeIdentifier` is a string generated by the native graph server
(likely a UUID) and published as part of the analyzer node's state via the
`/namedPipeIdentifier` JSON field. The Electron renderer reads this identifier
from the node state and opens the corresponding `/tmp/{id}` file.

Evidence for the `/tmp/` prefix: the constructor at ELF VA 0x20f6100 calls
`std::operator+("/tmp/", ...)` to concatenate the prefix with the identifier,
then calls `mkfifo(path, 0666)` on the result.

## Lifecycle

### Construction (ELF VA 0x20f6100)

1. Initialize vtable pointer to NamedPipeUnix vtable
2. Set state to 0 (disconnected)
3. Initialize iostream base (streambuf)
4. Concatenate `"/tmp/" + identifier` to form the path
5. Call `mkfifo(path, 0666)` -- creates the POSIX FIFO
   - Throws `"failed to create named pipe"` on failure
6. Call `pipe()` to create an anonymous pipe pair for interrupt signaling
   - Throws `"failed to create anonymous pipe for signaling"` on failure
7. Store the interrupt pipe FDs
8. Set the read end of the interrupt pipe to non-blocking (`O_NONBLOCK` via
   `fcntl(fd, F_SETFL, flags | O_NONBLOCK)`)

### TryConnect (ELF VA 0x20f6cd0)

Called to attempt opening the FIFO for writing:

1. If already in state 2 (connected), return success immediately
2. Get the FIFO path from the stored string
3. Call `open(path, O_WRONLY | O_NONBLOCK)` (flags = 0x801)
4. If open succeeds (fd > 0):
   - Set state to 2 (connected)
   - Store the file descriptor at offset 0x12c (300 decimal)
   - Return 1 (success)
5. If open returns -1 with `errno == ENXIO` (6):
   - Set state to 1 (no reader yet -- FIFO has no reader connected)
   - Return 0 (not yet connected, but not an error)
6. Otherwise: throw `"unknown error occured while trying to open named pipe
   for writing: {strerror(errno)}"`

The ENXIO case is normal during startup -- the native side creates the FIFO
before the Electron renderer has opened it for reading.

### Write (ELF VA 0x20f6f00)

Writes data to the connected FIFO with poll-based I/O:

1. Assert state == 2 (connected), else throw `"named pipe not connected"`
2. Get the pending data from the internal iostream buffer
3. If buffer is empty, return immediately
4. Set up a `pollfd` array with two entries:
   - `pollfd[0]` = { fd=fd_write, events=POLLOUT }
   - `pollfd[1]` = { fd=fd_interrupt_rd, events=POLLIN }
5. Call `poll(fds, 2, timeout_ms)` where timeout comes from param_2
   - This allows the write to be interrupted by writing to the interrupt pipe
6. If the interrupt pipe has data (`revents & POLLIN`):
   - Read 1 byte from interrupt pipe to acknowledge
   - Possibly retry or return
7. If the write fd is ready:
   - `write(fd_write, data, min(len, 0x1000))` -- writes up to 4096 bytes
   - On EAGAIN (errno 11): not an error, just means FIFO is full
   - On other error: throw `"write returned an unknown error: {strerror}"`
   - After partial write, consume written bytes from buffer, update
     pending_bytes counter at offset 0x128
   - Remaining data stays in the buffer for the next write call

The 4096-byte write limit matches the POSIX pipe buffer atomicity guarantee
(`PIPE_BUF` is typically 4096 on Linux).

### Destruction (ELF VA 0x20f6400, function `~NamedPipeUnix`)

1. Close the FIFO write fd (offset 300) if non-zero
   - Log warning on close error: `"unable to close named pipe handle, error: "`
2. Close the interrupt pipe read fd (offset 0x134) if non-zero
   - Log warning: `"unable to close interrupt pipe read handle, error: "`
3. Close the interrupt pipe write fd (param_1[0x26]) if non-zero
   - Log warning: `"unable to close interrupt pipe write handle, error: "`
4. Call `unlink(path)` to remove the FIFO from `/tmp/`
   - Log warning: `"unable to delete named pipe, error: "`
5. Free the path string
6. Destroy the iostream/streambuf base classes

The destructor uses source line annotations (0x30, 0x38, 0x40, 0x46) from
`named_pipe_unix.cpp` and function name `~NamedPipeUnix` in log messages.

## Reader Side (Electron Renderer)

From `bundle.js` analysis, the `handlePipe` function (module 1357) implements
the reader:

```javascript
// Simplified from minified bundle.js
const handlePipe = (pipeId, onData, onReconnect) => {
    const state = { canceled: false };

    (async () => {
        // On Linux, use POSIX named pipe reader:
        while (!state.canceled) {
            const fd = await fs.promises.open(`/tmp/${pipeId}`,
                fs.constants.O_RDONLY | fs.constants.O_NONBLOCK);
            const socket = new net.Socket({ fd: fd.fd, readable: true, writable: false });

            socket.on('data', (chunk) => {
                if (!state.canceled) {
                    onData(chunk.toString('utf-8'), socket);
                }
            });

            // Wait for socket to close/error
            const result = await waitForClose(socket);
            fd.close();
            if (result === 'closed') break;
        }
    })();

    return () => { state.canceled = true; };  // teardown function
};
```

Key points:
- The reader opens `/tmp/{namedPipeIdentifier}` with `O_RDONLY | O_NONBLOCK`
- It wraps the fd in a Node.js `net.Socket` for event-driven reading
- Data arrives as UTF-8 text (it's analyzer terminal output)
- If the FIFO closes, the reader breaks out of the loop
- A Windows variant (`u`) exists using a different mechanism
- The reader retries with 50ms sleep if open fails (writer not ready yet)

## Framing Protocol

**There is no framing protocol.** The named pipe carries raw UTF-8 text as a
byte stream. There are no length prefixes, no delimiters, no message
boundaries. The data is analyzer terminal output that gets written directly to
an xterm.js terminal widget in the Electron UI.

This makes the named pipe fundamentally different from the main IPC protocol
(which is JSON-based with message envelopes). The named pipe is a raw text
stream, not a structured protocol.

## Integration with Graph System

Named pipes are used by two types of graph nodes:

### Legacy Analyzers (AnalyzerNode)

The analyzer node state includes `/namedPipeIdentifier` (seen in the state
serialization function at ELF VA 0x2c9a050). When a legacy analyzer is created,
the native side:

1. Generates a unique identifier
2. Creates a `NamedPipeUnix` instance with that identifier
3. Publishes the identifier in the node state
4. The `StreamTerminal` function (at ELF VA 0x1c6a0f0 in analyzer_node.cpp,
   line 0x84f) writes analyzer output frames to the pipe

The `StreamTerminal` function:
- Checks if the pipe pointer at offset `0xb60` is non-null
- Calls a virtual method on the pipe to attempt connection (TryConnect)
- Sleeps briefly if not yet connected, retrying
- Logs `"named pipe connected"` on success
- Locks a mutex at offset `0x9f8` and processes analyzer frames
- For each frame, calls through function pointers to format data and write
  to the pipe
- Uses a backpressure mechanism: if the pipe's pending buffer exceeds 0x1000
  (4096) bytes, it pauses sending and calls `sched_yield()` in a loop waiting
  for the pipe to drain (with `write(pipe, -1)` timeout)
- Limits iterations to 10000 before resetting to prevent infinite loops

### High-Level Analyzers (HLA)

The `HighLevelAnalyzer` constructor takes a `Saleae::NamedPipe*` parameter
(from RTTI: `ZN6Saleae5Graph17HighLevelAnalyzerC1E...PNS_9NamedPipeE`).
HLAs receive a pipe pointer and can write their Python-generated output to it.

The HLA state also includes `/namedPipeIdentifier` (seen at ELF VA 0x1b3d2d0,
offset 600 in the state structure).

## PipeDock (Internal Graph Pipe System)

Distinct from the named pipe mechanism, the graph system has an internal
`PipeDock` system for passing typed data between graph nodes:

- `Saleae::Graph::Detail::PipeDockInternals` -- manages internal pipe
  connections
- `FindOrCreateCompoundPipe` -- creates compound pipes between nodes
- `mConnectedOutputs` / `mExternalPipeDock` -- track pipe connections
- Assertion: `"A pipe in mConnectedOutputs should always exist in mExternalPipeDock"`

These internal pipes carry structured data (AnalogData, DigitalData, VectorData,
etc.) between graph nodes. They are NOT POSIX named pipes and should not be
confused with the NamedPipe class documented here.

## Data Flow

```
Native Graph Server (libgraph_server_shared.so)
  |
  | AnalyzerNode / HlaNode
  |   creates NamedPipeUnix("/tmp/{uuid}")
  |   mkfifo("/tmp/{uuid}", 0666)
  |   publishes {uuid} in node state as /namedPipeIdentifier
  |
  |   StreamTerminal() loop:
  |     TryConnect() -> open("/tmp/{uuid}", O_WRONLY|O_NONBLOCK)
  |     write(fd, analyzer_output, min(len, 4096))
  |
  v
POSIX FIFO (/tmp/{uuid})
  |
  v
Electron Renderer (bundle.js)
  |   handlePipe(uuid, onData):
  |     open("/tmp/{uuid}", O_RDONLY|O_NONBLOCK)
  |     net.Socket({ fd, readable: true })
  |     socket.on('data', chunk => terminal.write(chunk))
  |
  v
xterm.js Terminal Widget (analyzer output panel)
```

## Relevance to RE

**Low priority for USB RE.** Named pipes are purely an analyzer terminal output
mechanism. They do not carry USB commands, device state, calibration data, or
capture samples. The main IPC uses DriveRequest/PopResponse (in-process) or
WebSocket (out-of-process). Understanding named pipes completes the IPC picture
but does not unlock any USB protocol knowledge.
